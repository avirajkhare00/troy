iOS · MLX Swift · on-device

Train on your Mac. Run it on your iPhone.

The model you fine-tuned with Troy doesn’t have to stay on the Mac. troy export -f ios packages it for MLX Swift — the same weights, generating on the iPhone’s GPU, with no server and no network. Airplane mode is the demo.

One command, validated for the phone

Fusing the adapter is the easy half. The exporter also checks the three things that decide whether an iPhone will actually load the result — before you find out in Xcode.

Architecturethe fused model_type must be in mlx-swift-lm’s registry (~60 architectures: Qwen, Llama, Gemma, Phi, Mistral, …)
Tokenizertokenizer.json + tokenizer_config.json present — swift-transformers builds the tokenizer from them on device
Memory fit≤ ~2 GB loads comfortably; up to ~4 GB needs the Increased Memory Limit entitlement; beyond that it says so plainly
README-iOS.mdwritten into the export: the Swift loading snippet and the Xcode entitlement steps

Rule of thumb: the export is 8-bit, so budget ~1.1 GB per billion parameters — a 1–2B model is the sweet spot for 8 GB-RAM iPhones. troy export -f ios tells you where you stand.

The Swift side is a dozen lines

The export is a folder mlx-swift-lm loads directly — bundle it for development, or troy push it and download on first launch.

Tool calling is the fine-tune that matters on a phone

Small models run on iPhones; small models are also unreliable tool callers out of the box — wrong argument names, invented tools, malformed JSON. That gap is exactly what a LoRA closes, and it’s measurable, not vibes. Troy ships the whole loop:

  1. troy data synth -f tools

    Point it at your tool schemas and a task description; a local teacher writes validated scenarios — direct calls, multi-step chains, clarifying questions for missing arguments, and answers that need no tool — each with a short <think> reasoning trace.

  2. troy train  ·  troy export -f ios

    Fine-tune a 1–2B base and package it. On our travel-planner demo, a tuned Qwen3-1.7B calls the right tool with the right arguments — and asks a clarifying question when the request is missing one.

  3. examples/ios

    Two working SwiftUI apps in the repo: TroyChat (chat with any Troy export) and TroyTravel (a trip planner whose tool calls build a live itinerary — mock data, real tool calling).

The gotchas, so you skip them

Everything below bit us while building the example apps. It’s all handled or documented in the repo — the short version:

  1. physical device only

    MLX kernels need a real GPU; the iOS simulator has none. Xcode 26 also needs two one-time downloads: the iOS platform and the Metal Toolchain (xcodebuild -downloadComponent MetalToolchain).

  2. memory entitlements

    Models over ~2 GB need Increased Memory Limit. Free personal teams can’t sign Extended Virtual Addressing — the example apps ship without it. Keep MLX’s cache small on iOS: cached buffers count against the app’s memory limit.

  3. match training at inference

    Greedy decoding keeps a small fine-tune’s tool-calling deterministic. And if your training data has empty think blocks, disable thinking at inference — or synthesize traces with troy data synth -f tools so the model learns to think and stop.

  4. never fuse into 4-bit

    Fusing a LoRA straight into 4-bit weights erases the adapter — the deltas drown in quantization noise and the export silently behaves like the base model. troy export -f ios handles it: dequantize-fuse, then requantize at 8 bits, which we verified preserves tuned behavior (6 bits already degrades it).

And now the iPhone trains back: the mesh

Running the model is half the loop. troy mesh closes the other half — idle iPhones on your Wi-Fi generate the training data. The Mac only coordinates: it mints teacher prompts and validates results with exactly the troy data synth parsing; every phone runs the teacher on its own GPU.

Workers are dumbthe coordinator renders every teacher prompt server-side; phones just complete text and send it back — your documents never leave the Mac un-chunked
Dropout-proofleased work requeues automatically when a phone locks, backgrounds, or leaves — kill a worker mid-run and the count still gets there
Same validationmalformed and duplicate generations are rejected centrally with the exact data synth code path — the output is a normal train.jsonl
Any Apple deviceiPhones join via the TroyWorker app, Macs via troy mesh join — mix freely, one shared token

Phones make the dataset, the Mac trains on it, the phones run the result. A drawer full of old iPhones is a data-generation cluster now.

The whole loop is local: iPhones generate, Mac trains, iPhones run.
